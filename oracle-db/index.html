Backup & restore (Data Pump)

Data Pump (expdp/impdp) replaced the old exp/imp tools — faster, parallel, and the standard way to move data in and out of Oracle today.

# full database exportexpdp <username>/<password>@<tns_alias> directory=DATA_PUMP_DIR dumpfile=full_%U.dmp logfile=export.log full=y
# export just one schemaexpdp <username>/<password>@<tns_alias> schemas=<SCHEMA_NAME> directory=DATA_PUMP_DIR dumpfile=schema.dmp logfile=export_schema.log
# export a single tableexpdp <username>/<password>@<tns_alias> tables=<SCHEMA_NAME>.<TABLE_NAME> directory=DATA_PUMP_DIR dumpfile=table.dmp
# everything above as a parameter file instead of a long command lineexpdp <username>/<password>@<tns_alias> parfile=export.par

export.par contents, for reference:

SCHEMAS=<SCHEMA_NAME>
DIRECTORY=DATA_PUMP_DIR
DUMPFILE=schema_%U.dmp
LOGFILE=export_schema.log
PARALLEL=4
COMPRESSION=ALL
# import a Data Pump dumpimpdp <username>/<password>@<tns_alias> directory=DATA_PUMP_DIR dumpfile=schema.dmp logfile=import.log
# import into a differently-named schemaimpdp <username>/<password>@<tns_alias> parfile=import.par remap_schema=<OLD_SCHEMA>:<NEW_SCHEMA>
# don't actually importimpdp <username>/<password>@<tns_alias> directory=DATA_PUMP_DIR dumpfile=schema.dmp sqlfile=preview.sql
-- confirm the DIRECTORY object exists and points where expectedSELECT directory_name, directory_path FROM dba_directories;
Enhanced — RMAN (the actual database-level backup tool, separate from Data Pump's logical export) 
# connect to the target databaserman target /
# full backuprman target / <<< "BACKUP DATABASE PLUS ARCHIVELOG;"
# same, and delete archive logs once safely backed uprman target / <<< "BACKUP DATABASE PLUS ARCHIVELOG DELETE INPUT;"
# see what backups actually exist and when they ranrman target / <<< "LIST BACKUP SUMMARY;"
# dry-run a restore without touching anythingrman target / <<< "RESTORE DATABASE VALIDATE;"

Data Pump exports data (logical, portable across versions/platforms, good for migrations and single-schema restores). RMAN backs up the database itself (physical, faster for full disaster recovery, what you'd actually reach for to restore a crashed instance). Know which one a given situation calls for — they solve different problems.

Health check
  1. Instance status — SELECT open_mode FROM v$database; — red flag: anything other than READ WRITE when you expect the DB to be fully open.
  2. Session count — SELECT count(*) FROM v$session; — red flag: approaching sessions parameter limit — new connections will start failing soon.
  3. Tablespace usage — dba_tablespace_usage_metrics — red flag: any tablespace above 90% used.
  4. Alert log — tail the current alert log — red flag: any ORA- error, especially repeating ones — a single old one in history is not urgent, a fresh repeating one is.

Troubleshooting

Database won't accept connections:

# is the listener even uplsnrctl status
# is the instance actually open, or stuck in MOUNTsqlplus / as sysdba <<< "SELECT status FROM v\$instance;"

Archiver stuck / "ORA-00257: archiver error":

-- almost always the recovery area filling upSELECT * FROM v$flash_recovery_area_usage;
# clear old archived logs older than 3 daysrman target / <<< "DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-3';"

Tablespace full:

-- confirm which tablespace firstSELECT tablespace_name, ROUND(used_percent, 1)
  FROM   dba_tablespace_usage_metrics
  WHERE  used_percent > 90;
-- add space to the tablespaceALTER TABLESPACE mytablespace ADD DATAFILE '/path/to/new_datafile.dbf' SIZE 500M AUTOEXTEND ON;
