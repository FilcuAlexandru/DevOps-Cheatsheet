Logs

23 COMMANDS INDEXED

Application/system log files on disk — searching, following, rotating. (For systemd's own journal, see the separate systemd section — journalctl is a different mechanism entirely.)

# follow a single log file livetail -f /var/log/myapp/app.log
# follow multiple files at once, each line prefixed with its filenametail -f /var/log/myapp/*.log
# case-insensitive search in a plain log filegrep -i "error" /var/log/myapp/app.log
# recursive search across a whole log directory, with line numbersgrep -rn "connection refused" /var/log/myapp/
# search inside a rotated, gzip-compressed log without manually decompressing itzgrep "timeout" /var/log/myapp/app.log.2.gz
# every log file modified in the last 24h, across the systemfind /var/log -name "*.log" -mtime -1
# find unexpectedly large log files eating diskfind /var/log -name "*.log" -size +100M
# print only lines within a time window, useful on huge logs where grep -A/-B isn't precise enoughawk '/2026-09-10 14:0/,/2026-09-10 14:1/' app.log
# even for app logs, check whether the app is actually logging to the journal instead of a filejournalctl --since "10 minutes ago" -o cat
# first 100 lines — useful for checking a log's format/header before writing a real filterhead -n 100 app.log
Enhanced 
# 5 lines of context before and after a match — the surrounding lines are usually what actually explains itgrep -A5 -B5 "OutOfMemoryError" app.log
# follow a file live, filtered to just error lines (--line-buffered keeps grep from batching output when piped)tail -n +1 -f app.log | grep --line-buffered "ERROR"
# search across several rotated archives at once, in the order they happenedzcat app.log.1.gz app.log.2.gz | grep "user_id=12345"
# truncate a live log file in place, safe even while a process still has it open — rm would just hide the space until the process exits: > /var/log/myapp/app.log

Log rotation (logrotate):

# see how a specific app's rotation is configured — size/age thresholds, compression, retention countcat /etc/logrotate.d/myapp
# dry-run: shows what WOULD happen, without actually rotating anythinglogrotate -d /etc/logrotate.d/myapp
# force an out-of-cycle rotation right now, useful before a disk fills uplogrotate -f /etc/logrotate.d/myapp

Health check
  1. Is anything actually writing logs — tail -f /var/log/myapp/app.log and watch for fresh lines during known activity — red flag: silence despite active traffic — the app may be logging somewhere else entirely.
  2. Disk headroom for logs — df -h /var/log — red flag: above 90% — rotation may not be keeping up.
  3. Rotation is actually running — check the log file's size and timestamp against what logrotate config expects — red flag: a file far past its configured rotation size/age means rotation silently isn't firing.

Troubleshooting

Can't find where an app actually logs to:

# list open files for the process — its log file(s) show up here even with a nonstandard pathlsof -p <pid> | grep -i log
# files touched in the last 5 minutes — catches an active log you don't know the location offind / -xdev -name "*.log" -newer /tmp -mmin -5 2>/dev/null

A single log file has grown huge and is filling the disk:

# truncate in place, safe even if a process still has it open — see the Enhanced note above: > /var/log/myapp/app.log
# if rotation should have caught this already, force it and check why it didn't run on schedulelogrotate -f /etc/logrotate.d/myapp

Searching a large log is too slow:

# -F (fixed string) skips regex parsing — much faster when you're not actually using regex featuresgrep -F "exact string" bigfile.log
# ripgrep, if available — multithreaded and typically far faster than grep on large filesrg "pattern" bigfile.log
