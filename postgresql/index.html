Backup & restore

 
# plain SQL, human-readablepg_dump -h <host> -U <username> -d <database> -Fp > backup.sql
# custom formatpg_dump -h <host> -U <username> -d <database> -Fc -f backup.dump
# directory format, dumped in parallel with 4 jobspg_dump -h <host> -U <username> -d <database> -Fd -j 4 -f backup_dir
# every database in the cluster, plus roles/tablespacespg_dumpall -h <host> -U <username> > full_cluster.sql
# structure only, no datapg_dump --schema-only -h <host> -U <username> -d <database> > schema.sql
# data only, no structurepg_dump --data-only -h <host> -U <username> -d <database> > data.sql
# a single table, not the whole databasepg_dump -t <schema>.<table> -h <host> -U <username> -d <database> > table.sql
# restore a plain-SQL dumppsql -h <host> -U <username> -d <database> -f backup.sql
# restore a custom-format dumppg_restore -h <host> -U <username> -d <database> backup.dump
# parallel restore from directory formatpg_restore -h <host> -U <username> -d <database> -j 4 backup_dir
# list the contents of a dump without restoring anythingpg_restore -l backup.dump
# restore just one table out of a full dumppg_restore -h <host> -U <username> -d <database> -t <table> backup.dump
Enhanced — physical backups (pg_basebackup) 
# full physical copy of the data directory, streaming WAL as it goespg_basebackup -h <host> -U <username> -D /backup/path -Fp -Xs -P
# same idea, but tarred and gzip-compressed outputpg_basebackup -h <host> -U <username> -D /backup/path -Ft -z -P

pg_dump is a logical backup — portable across versions, good for migrations and picking out individual tables, but it's a point-in-time SQL/data snapshot with no way to replay changes since. pg_basebackup is a physical backup — combined with WAL archiving, it supports true point-in-time recovery (restore to any specific moment, not just the backup time). Know which one the situation actually calls for: routine migrations and table-level restores want pg_dump; disaster recovery for the whole cluster wants a physical backup strategy.

Health check
  1. Connection count — SELECT count(*) FROM pg_stat_activity; — red flag: approaching max_connections — new connections are about to start failing.
  2. Long-running queries — filter pg_stat_activity by now() - query_start — red flag: queries running far longer than your normal workload's baseline.
  3. Replication lag (if you have standbys) — pg_stat_replication — red flag: lag bytes climbing over successive checks, not just momentarily nonzero.
  4. Autovacuum keeping up — check pg_stat_user_tables for n_dead_tup — red flag: dead tuple count growing faster than autovacuum clears it — bloat and slow queries follow.

Troubleshooting

"too many connections" errors:

-- see where connections are actually goingSELECT count(*), state
  FROM   pg_stat_activity
  GROUP  BY state;
-- long-idle connections usually mean pool misconfigurationSELECT pid, state, now() - state_change AS idle_for
  FROM   pg_stat_activity
  WHERE  state = 'idle'
  ORDER  BY idle_for DESC
  LIMIT  10;

Replication lag growing:

-- confirm lag is actually growing over successive checksSELECT client_addr, pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
  FROM   pg_stat_replication;

Check the standby's own disk I/O and network to the primary — lag is almost always a resource bottleneck on the replica, not the primary doing anything wrong.

Query stuck / deadlock suspected:

-- who's waiting, and on what kind of lockSELECT pid, query, state, wait_event_type
  FROM   pg_stat_activity
  WHERE  wait_event_type = 'Lock';
-- terminate the blocking session once you've confirmed which one it isSELECT pg_terminate_backend(<pid>);
